# Локальный индекс документов (RAG, этап индексации)

**Корпус:** русскоязычный, тематика «разработка на платформе 1С:Предприятие».
**Результат:** векторный индекс FAISS + метаданные SQLite, две стратегии chunking,
функция поиска, количественное сравнение стратегий; RAG-агент на DeepSeek
с режимами «с RAG / без RAG» и контрольным набором из 10 вопросов (раздел 8).

---

## 1. Дополнения к формулировке задания

Задание покрывает только индексацию и требует «сравнить 2 стратегии», не задавая
критериев сравнения. Добавлено минимально необходимое для проверяемого результата:

- функция `search(query, k)` — без неё сравнение стратегий не имеет предмета;
- 10 тестовых вопросов с размеченными релевантными фрагментами (ground truth);
- метрики: Recall@5, MRR@5, статистика размеров, целостность границ чанков.

LLM на этом этапе не используется и не требуется: эмбеддинги — encoder-модель,
сравнение — по embedding-сходству и ручной разметке.

## 3. Пайплайн

```javascript
corpus/ → ingest.py → chunking.py → build_index.py → index/ (FAISS + SQLite)
                                                        ↓
                              search.py ← evaluate.py (10 вопросов)
```

### 3.1 Ingestion (`src/ingest.py`)

Адаптеры по формату, единый выход: `doc_id, source, title, type, url, text`.

- **md:** удаление картинок, ссылки→текст, остатки HTML; заголовок из первого `#`.
- **pdf:** PyMuPDF; фильтр boilerplate: колонтитулы журналов, номера страниц,
строки в битой кодировке (mojibake без кириллицы — реальный дефект одного из PDF).
- **code:** текст как есть; структура извлекается на этапе chunking.

Тип документа определяется **расширением** (`.os`→code, `.pdf`→pdf, `.md`→
md-ветка независимо от имени). Первоначальная классификация по префиксам имён
(`readme_`/`habr_`/`va_`) отправляла любой новый md-файл в pdf-эвристику
заголовков, где markdown-структура не распознавалась и документ молча
деградировал до fixed-нарезки — дефект найден при добавлении личного
документа и исправлен на этапе RAG-агента.

### 3.2 Chunking (`src/chunking.py`)

Токенизатор — от `intfloat/multilingual-e5-large` (та же модель, что и эмбеддинги,
счёт в токенах модели, не в символах).

**Стратегия 1 — fixed.** Окна по 512 токенов, перекрытие 77 токенов (15%).
Конец окна притягивается к ближайшему пробелу (≤20 токенов), чтобы не резать
слова. Предложения и абзацы режутся — это осознанный, измеряемый дефект стратегии.

**Стратегия 2 — structural.** Границы по структуре документа:

| Тип документа | Границы |
| --- | --- |
| md (статьи, документация, README) | заголовки `#`–`######`, путь раздела сохраняется |
| code (.os) | `Процедура/Функция … КонецПроцедуры/КонецФункции` |
| pdf | эвристика: Введение/Заключение/Выводы/…, строки КАПСОМ, нумерованные заголовки (без запятых и финальной точки — отсекает библиографию) |

Разделы >512 токенов дорезаются окнами с overlap 15%; разделы <80 токенов
склеиваются с соседями (иначе — мусорные микрочанки).

### 3.3 Эмбеддинги и хранение (`src/build_index.py`)

- Модель: `intfloat/multilingual-e5-large`, dim=1024, CPU.
Префиксы обязательны для e5: `passage:` для документов, `query:` для запросов.
- FAISS `IndexFlatIP` по нормированным векторам = косинусное сходство.
- FAISS хранит **только векторы**. Метаданные и текст — в SQLite
(`index/meta.db`), связь по порядковому id.
- JSON (`index/index_{strategy}.json`, модуль `src/storage.py`) — полный
переносимый дамп: метаданные + текст + векторы каждого чанка (4.5–5.9 МБ
на стратегию). Из JSON индекс восстанавливается без модели и без FAISS;
поиск по JSON реализован бэкендом `json` (numpy cosine) и проверен на
эквивалентность FAISS (top-5 и скоры совпадают).

Итого три хранилища с разными ролями: FAISS — быстрый поиск,
SQLite — запросы к метаданным, JSON — переносимость и инспекция.

**Метаданные каждого чанка:** `chunk_id, doc_id, source, title, section, type,
char_start, char_end, n_tokens, text` — требуемый набор + смещения в документе.

Время построения (CPU): fixed — 1121 с, structural — 1152 с.

## 4. Сравнение стратегий

### 4.1 Геометрия чанков

| Метрика | fixed | structural |
| --- | --- | --- |
| Чанков | 353 | 507 |
| Средний размер, ток. | 494 | 293 |
| Стд. отклонение | 64 | 162 |
| min / max | 126 / 512 | 80 / 512 |

fixed — плотные однородные чанки; structural — вдвое меньше в среднем,
сильный разброс (естественный размер разделов/процедур), +44% к числу чанков
(дороже хранение и поиск, хотя на этом объёме несущественно).

### 4.2 Целостность границ (выборка 120 чанков)

| Доля чанков с обрывом предложения | fixed | structural |
| --- | --- | --- |
| в начале чанка | 64.2% | 20.0% |
| в конце чанка | 83.3% | 30.8% |

У structural ненулевые значения — из-за вторичной дорезки разделов >512 токенов;
у fixed обрыв — норма, а не исключение. Для LLM на этапе генерации обрыв
контекста = прямая деградация ответов.

### 4.3 Retrieval (10 вопросов, ручная разметка)

| Метрика | fixed | structural |
| --- | --- | --- |
| **Recall@5** | **0.7** | **0.9** |
| MRR@5 | 0.70 | 0.63 |
| Средний ранг первого релевантного | 1.0 | 2.0 |
| Найдено вопросов (любой ранг ≤ 20) | 7 | 9 |

По вопросам (ранг релевантного чанка; «—» = не в top-5):

| # | Тема | fixed | structural |
| --- | --- | --- | --- |
| 1 | Дымовые тесты (va_smoke) | 1 | 1 |
| 2 | Что такое OneScript (readme) | 1 | 1 |
| 3 | Запуск приложения (код 1commands) | — | 4 |
| 4 | Уровни логирования (код logos) | — | 4 |
| 5 | Тестирование 1С:ERP, Jenkins (pdf) | 1 | 1 |
| 6 | Примитивные типы данных (pdf) | 1 | 3 |
| 7 | COMConnection (habr) | 1 | 1 |
| 8 | Fuzzy-поиск, транслит (habr) | 1 | 1 |
| 9 | Видеоинструкции (va) | 1 | 2 |
| 10 | Синтакс-помощник (pdf) | — | — |

**Разбор промахов:**

- Вопросы 3–4 (код): fixed режет файл по 512 токенов, разрывая процедуры и
смешивая несвязный код в одном окне — нужный фрагмент «растворяется».
structural держит процедуру целиком → находит (ранг 4).
- Вопрос 10 (синтакс-помощник): промахнулись обе. Диагностика: релевантный
чанк на 20-м (fixed) / 12-м (structural) месте. Причина — три PDF о языке 1С
образуют один семантический кластер, а нужная статья упоминает предмет
вскользь. Это честный предел dense-retrieval на близких документах,
лечится reranker'ом или гибридным поиском (BM25 + векторы).

### 4.4 Выводы

1. **Для смешанного корпуса (проза + код) structural лучше по recall: 0.9 vs 0.7.**
Решающий фактор — код: структурные границы процедур против слепых окон.
2. **fixed точнее в top-1, когда находит** (mean rank 1.0 vs 2.0, MRR 0.70 vs 0.63):
крупные чанки несут больше контекста → сильное сходство. Но цена — промахи.
3. Для RAG важнее **recall**: ненайденный фрагмент никакой reranker не спасёт,
а ранги 2–4 лечатся reranker'ом. → structural как рабочая стратегия,
fixed — честный baseline.
4. Практическое улучшение structural (вне рамок задания): overlap между
соседними разделами и гибридный поиск для близких по теме документов.

## 5. Ограничения

- 10 вопросов — малая выборка; разница 0.7/0.9 показательна, но не статистически
строга. Для вывода уровня «production» нужно 50+ вопросов.
- PDF-эвристика заголовков несовершенна (нумерованные списки могут приниматься
за заголовки; склейка микроразделов даёт составные имена вида «A / B»).
- e5-large на CPU — 19 минут на стратегию; на GPU — секунды. Для учебного
объёма приемлемо, для больших корпусов — нет.
- Эмбеддинги кода русскоязычной моделью — рабочий, но не оптимальный вариант;
специализированные code-embeddings могли бы поднять recall по коду.

Воспроизведение: `pip install -r requirements.txt` →
`python3 build_index.py` → `python3 evaluate.py`.
Для агента: переменная окружения `DEEPSEEK_API_KEY` → `python3 eval_answers.py`
(или страница «Агент» в веб-UI).

## 7. Веб-интерфейс (Flet)

`src/ui_app.py`, Flet 1.0, web-режим. Запуск:

```bash
python3 src/ui_app.py                # http://127.0.0.1:8550
python3 src/ui_app.py --host 0.0.0.0 --port 9000   # переопределение
```

Host по умолчанию — 127.0.0.1. Прямые URL: `/`, `/agent`, `/admin`, `/logs`.

**Страница «Поиск».** Поле запроса, выбор стратегии (structural/fixed),
бэкенда (faiss/json), k. Результаты — карточки: score (цвет по порогу),
source, тип, путь раздела, разворачиваемый полный текст чанка. Модель
эмбеддингов предзагружается в фоне при старте (первый поиск без ожидания
~1 мин). Бэкенд `json` ищет по JSON-дампу через numpy — результаты
идентичны FAISS, чуть медленнее (на этом объёме — миллисекунды разницы).

**Страница «Агент».** Вопрос, режим (Сравнение / С RAG / Без RAG), конвейер
(обычный / порог / реранк / rewrite / всё вместе — раздел 9), движок реранкера
(LLM / cross-encoder), стратегия, бэкенд, k. Ответы DeepSeek — карточки: режим, модель, токены (вх./исх.), время
ответа; у RAG-режима — статистика конвейера (кандидатов → после порога → в
контекст, переписанный запрос) и список использованных источников. Режим
«Сравнение» выполняет оба вызова последовательно и показывает ответы рядом.
При открытии страницы показывается фактическая видимость `DEEPSEEK_API_KEY`
процессом (зелёное/красное состояние); без ключа вызовы LLM не выполняются.

**Страница «Администрирование».** Таблица корпуса (26 документов, тип, объём),
статистика индексов по стратегиям (чанков, ср./мин./макс. токенов, размеры
FAISS и JSON), кнопки пересборки: fixed / structural / оба. Пересборка —
изолированный subprocess (`build_index.py`), прогресс пишется в
`logs/build.log`, кнопки блокируются на время работы (на CPU ~20 мин
на стратегию). По завершении JSON-дампы обновляются автоматически.

**Страница «Логи и просмотр индексов».** Источник на выбор: `app.log`,
`build.log`, `индекс: fixed`, `индекс: structural`. Для логов: хвост 400 строк
(моноширинный), фильтр по уровню, автообновление 3 с, очистка. Для индексов:
полный список чанков (chunk_id, тип, источник, раздел, токены, превью текста) —
инспекция содержимого индекса; фильтр уровней и очистка при этом отключаются.
Логируются: старт UI, загрузка модели, открытие страниц, каждый поиск
(запрос, стратегия, бэкенд, k, hits, top-score, latency), просмотры индексов,
пересборки, ошибки.

Особенности реализации: асинхронный `main` (Flet 1.x), блокирующие вызовы
(поиск, загрузка модели) — через `asyncio.to_thread`, UI не фризится;
статистика админки читается из SQLite без загрузки модели.

## 8. RAG-агент: первый RAG-запрос

### 8.1 Цепочка

```javascript
вопрос → search(top-k чанков) → build_messages(контекст + вопрос) → DeepSeek → ответ + источники
```

- `src/llm.py` — клиент DeepSeek API (OpenAI-совместимый):
`base_url=https://api.deepseek.com`, модель `deepseek-v4-pro`,
`temperature=0` (воспроизводимость сравнения), thinking-режим выключен
(reasoning-токены тарифицируются как output, для сравнения режимов не нужны),
non-stream, таймаут 120 с, до 2 повторов при 429/5xx, usage пишется в лог.
Ключ читается только из переменной окружения `DEEPSEEK_API_KEY`; при её
отсутствии — ошибка с инструкцией по настройке; ключ не логируется и никуда
не сохраняется.
- `src/rag_agent.py` — `ask(question, mode, strategy, backend, k)`. Режимы:
`plain` (вопрос напрямую в LLM) и `rag` (top-k чанков → контекст). System-prompt
у обоих режимов один и тот же (эксперт по 1С, русский язык, по существу) —
сравнение чистое, режимы различаются только наличием контекста.
- Промпт RAG-режима: контекст — пронумерованные чанки с заголовками
`[N] title — section (source)`; инструкции модели: опираться только на
контекст, помечать утверждения ссылками `[N]`, при отсутствии ответа в
контексте — прямо сообщить об этом, не додумывать.
- Размер контекста: 5 чанков × ≤512 токенов ≈ ≤2.6K токенов; при окне
модели 1M обрезка не требуется.

### 8.2 Контрольный набор (`tests/questions.json`, схема v2)

10 вопросов, для каждого зафиксированы:

- `expect` — ожидаемые ключевые факты с regex-алиасами (допускают
перефразирование; `match=all` для фактов-композиций из нескольких терминов);
- `sources` — источники, которые должны попасть в выдачу retrieval;
- `needle` — дословная подстрока релевантного чанка; используется
retrieval-метриками раздела 4.3 (совместимость с `evaluate.py` сохранена).
Все needle проверены: присутствуют в чанках ожидаемых источников.

Состав набора: 3 вопроса по личному документу (концепция регл. учёта — её
гарантированно нет в обучающих данных LLM), 4 по специфике корпуса
(Vanessa Automation ×2, Хабр ×2), 1 по коду (v8runner), 1 по PDF (авторы
статьи — факт, без корпуса не восстанавливается), 1 общеизвестный baseline
(OneScript).

Набор пересобран, а не взят из раздела 4.3: прежние вопросы — общеизвестные
факты о 1С, на них LLM отвечает из параметрической памяти и дельта режимов
не проявляется. Новый набор смещён в зону, где память модели заведомо слаба.

### 8.3 Оценка (`src/eval_answers.py`)

Прогон каждого вопроса в обоих режимах. Авто-проверка: доля найденных фактов
в ответе (hit по любому алиасу либо по всем для `match=all`) и попадание
ожидаемых источников в выдачу. Выход: `tests/results_*.json` (полные ответы +
usage) и `tests/results_*.md` (готовая таблица для этого отчёта).

Ограничение метода: regex-алиасы ловят факт только в ожидаемой
формулировке — автоматика даёт нижнюю оценку качества. Финальный вердикт
по каждой строке таблицы — ручной разбор.

Запуск (из `src/`):

```bash
# если DEEPSEEK_API_KEY ещё не задан в переменных среды:
setx DEEPSEEK_API_KEY "sk-..."   # Windows, постоянно; затем новая консоль
# проверка, что процесс видит ключ:
python -c "import os; print(bool(os.environ.get('DEEPSEEK_API_KEY')))"
python3 eval_answers.py          # все вопросы; выборочно: --only q1,q3
```

### 8.4 Результаты сравнения

Прогон выполняется локально — ключ API не покидает машину пользователя.
Готовая таблица `tests/results_*.md` после прогона вставляется в этот раздел.

Ожидаемая дельта (гипотеза для проверки): q1–q3 и q9 без RAG неотвечаемы —

## 9. Второй этап после поиска: фильтрация, реранкинг, query rewrite

### 9.1 Конвейер (`src/rerank.py`)

```javascript
вопрос → [query rewrite] → search(k_pre=20) → порог similarity → LLM-реранк → top k_post=5 → LLM-ответ
```

Режимы конвейера (параметр `pipeline` в `rag_agent.ask`):

| Режим | Что делает |
| --- | --- |
| `baseline` | как раньше: search(k=5), без второго этапа |
| `filter` | search(k_pre=20) → отсечение по порогу косинуса → top k_post |
| `rerank` | search(k_pre=20) → порог → LLM-реранк → top k_post |
| `rewrite` | вопрос переписывается в поисковый запрос → search(k=5) |
| `full` | rewrite → search(k_pre) → порог → реранк → k_post |

**Порог отсечения** — по косинусному скору e5 (стартовое `min_sim=0.75`;
скоры корпуса лежат в ~0.7–0.9). Гарантия `keep_min=1`: хотя бы один чанк
всегда остаётся, иначе RAG отвечал бы на пустом контексте и метрика
превратилась бы в мусор.

**Топ-K до и после:** `k_pre=20` кандидатов из retrieval → после фильтрации
и реранкинга `k_post=5` уходят в контекст LLM. Оба параметра конфигурируются
(`--k-pre`, `--min-sim` в eval; аргументы `run_pipeline`).

**LLM-реранкер** — listwise, один вызов DeepSeek на вопрос: все кандидаты
(заголовок + раздел + текст) отправляются одним запросом (~10–12K входных
токенов при 20 кандидатах), ответ — JSON `{"ranking": [...]}` через
`response_format={"type": "json_object"}`. Парсинг устойчив: вырезание
массива regex при невалидном JSON, фильтрация индексов вне диапазона и
дублей; неоценённые LLM фрагменты добираются в исходном порядке. Любой сбой
(LLM недоступен, мусор в ответе) — fallback на исходный порядок retrieval:
второй этап не имеет права ломать выдачу. Осознанное ограничение выбора:
у LLM-реранкера нет калиброванного скора, поэтому отсечение остаётся на
retrieval-стороне, реранкер только переупорядочивает.

**Cross-encoder-реранкер** (движок `ce`) — отдельная модель
`BAAI/bge-reranker-v2-m3` (~2.3 ГБ, ленивая загрузка один раз; лёгкая
альтернатива в коде: `DiTy/cross-encoder-russian-rubert-tiny2`, ~50 МБ).
Скор каждой пары (вопрос, чанк), сортировка по убыванию; скор сохраняется
в чанке (`ce_score`). Замерено: загрузка ~3.5 мин (первое скачивание),
инференс ~0.5 с/пару на CPU (20 кандидатов ≈ 10 с на вопрос). Скоры —
сигмоидальные вероятности: на контрольной тройке релевантный чанк 0.009
против ~0.000 у нерелевантных — абсолютные значения малы даже для верных
пар, поэтому CE-скор используется только для порядка, без порога по нему
(та же логика, что у LLM-движка). При сбое модели — fallback на исходный
порядок. Движок выбирается параметром `rerank_engine` ("llm" | "ce")
в `run_pipeline`/`ask`, флагом `--reranker` в eval и селектором «Реранкер»
на странице «Агент».

**Query rewrite** — один вызов DeepSeek (`temperature=0`): вопрос
переписывается в поисковый запрос с точной номенклатурой 1С (имена объектов
метаданных, регистров, документов). В поиск идёт переписанный запрос, в
промпт ответа — исходный вопрос. Оба варианта логируются. При сбое —
исходный вопрос.

### 9.2 Сравнение режимов (`src/eval_answers.py`, переработан)

Матрица: 10 вопросов × (plain + до 5 конвейеров). Два уровня метрик:

- **retrieval** (детерминированно, без оценки LLM): ранг needle-чанка в
выдаче конвейера → Recall и MRR по каждому конвейеру. Честно показывает
асимметрию: реранкер при k_pre=20→5 может поднять recall (поднимает найденное
с рангов 6–20 в top-5), порог может recall только снизить — это видно в
таблице;
- **ответы**: доля найденных ключевых фактов (regex-алиасы) по каждому
конвейеру + контроль источников.

Запуск (из `src/`):

```bash
python3 eval_answers.py                          # вся матрица, реранкер LLM
python3 eval_answers.py --reranker ce            # вся матрица, реранкер cross-encoder
python3 eval_answers.py --pipelines baseline,full        # минимальное сравнение
python3 eval_answers.py --min-sim 0.78 --k-pre 30        # калибровка порога
```

Выход: `tests/results_pipes_*.json` (полные ответы, статистика конвейеров,
переписанные запросы) и `tests/results_pipes_*.md` (две таблицы для отчёта).

### 9.3 Результаты сравнения

Заполняется после локального прогона: таблицы из `results_pipes_*.md`
вставляются сюда.

Гипотезы для проверки:

1. `rerank`/`full` поднимут retrieval-метрики против baseline за счёт
k_pre=20: кандидат с рангом 6–20 получает шанс попасть в top-5 (сценарий
вопроса 10 из раздела 4.3 — там релевантный чанк сидел на 12-м месте).
2. `filter` на этом корпусе recall не улучшит (порог только отсекает), но
сократит контекст от шумных чанков на неоднозначных вопросах — эффект виден
в fact-hits ответов, не в recall.
3. `rewrite` даст выигрыш на вопросах с разговорной формулировкой (q6, q7)
и нейтрален на точных терминологических (q2, q3).

## 10. Строгий режим: обязательные источники, цитаты и «не знаю»

### 10.1 Контракт ответа (`src/grounded.py`, `rag_agent.ask_grounded`)

Каждый ответ RAG теперь обязан содержать три компонента:

1. **ответ** — текст со ссылками `[N]` на чанки контекста;
2. **источники** — `[{chunk_id, source, title, section}]`, собираются
   **только из чанков, реально процитированных моделью** (ссылка на чанк,
   который модель не использовала, — ложная атрибуция);
3. **цитаты** — `[{chunk_id, source, section, quote, verified}]`: дословные
   фрагменты чанков, каждая **верифицируется автоматически как подстрока**
   текста чанка (`strict` — дословно с точностью до whitespace; `soft` —
   модель подменила типографику (тире/кавычки/ё), засчитывается как
   диагностика, не как подтверждение; `fail` — не цитата, источник по ней
   не засчитывается).

LLM отвечает строго JSON `{"answer": ..., "citations": [{"chunk", "quote"}]}`
(`response_format=json_object`, промпт `SYSTEM_GROUNDED`). Парсинг устойчив:
markdown-ограждения, текст вокруг JSON, висячие запятые, недопустимые
номера чанков отбрасываются. Статусы результата:

| status | смысл |
| --- | --- |
| `ok` | ответ + ≥1 источника с подтверждёнными цитатами |
| `low_relevance` | gate не пройден: «не знаю» без вызова LLM |
| `model_refusal` | gate пропустил, но модель признала контекст недостаточным («не знаю», цитаты пусты — по контракту) |
| `parse_error` | LLM вернула не-JSON (ответ показан как есть) |
| `no_verified_quotes` | содержательный ответ без единой подтверждённой цитаты — нарушение контракта |

### 10.2 Режим «не знаю»: два слоя, а не один порог

**Калибровка показала, что одного порога косинуса недостаточно.** Топ-скоры
10 рабочих вопросов — 0.85–0.90, трёх негативных (вне корпуса) — 0.776,
0.777 и **0.831**: neg3 (про BGP/Cisco) выше реального q2 (0.802 — до
пересборки индекса). Ни один абсолютный порог не разделяет эти множества
без ложных срабатываний. Поэтому контур двухслойный:

1. **Детерминированный gate** (`rerank.run_pipeline(gate_sim=...)`,
   калибровано 0.78 на этом корпусе): если топ-скор retrieval ниже порога,
   конвейер останавливается **до стадий реранка и генерации** — ноль
   вызовов LLM, ответ «Не знаю…» + явная просьба уточнить вопрос (с
   подсказкой ближайшей темы). Гарантия не зависит от послушания модели.
   Ранняя остановка внутри конвейера устраняет впустую потраченный вызов
   реранкера для отсечённых вопросов (проверено: вызовы LLM на негативных
   1 и 2 — ноль).
2. **Отказ на уровне модели** (правило 5 `SYSTEM_GROUNDED`) для зоны
   перекрытия скоров: контекст прошёл gate, но вопроса не покрывает —
   модель обязана вернуть «Не знаю…» с пустыми цитатами → `model_refusal`.

Прежняя гарантия `keep_min=1` в `apply_threshold` (контекст никогда не
пуст) оставлена для legacy-конвейеров, но grounded-режиму она не мешает:
gate смотрит реальные скоры, а не факт наличия чанков.

### 10.5 Как прогнан тест без DEEPSEEK_API_KEY в этой среде

Детерминированная часть (retrieval, gate, парсинг, верификация цитат,
сборка источников, метрики) покрыта автотестом
`tests/selftest_grounded.py` (25 проверок) и выполнена целиком. LLM-стадии
(реранк, генерация) в этой среде выполнены внешней моделью **ровно по
промптам проекта** (`SYSTEM_GROUNDED`, `_RERANK_SYS`), ответы сохранены в
`tests/grounded_llm/{qid}.txt|ranking.json` и подставлены через
`src/eval_grounded_stub.py` — тот же код конвейера, та же верификация.

Локальный прогон с DeepSeek (одна команда, файлы stub не нужны):

```bash
python3 eval_grounded.py --pipeline rerank --gate-sim 0.78   # из src/, DEEPSEEK_API_KEY в окружении
```

Важно: набор `tests/grounded_llm/` — это регрессионный эталон поведения
LLM, а не подмена продакшен-вызовов; при смене модели или промпта эталон
перегенерируется.
